# BUG-47 — AutoCommit op=commit 撞 index.lock 時 commits=0 且 blocked_repos=0 —— 跟「沒東西可收」同形

> `bug` / `wrong` / `open`　回報者：summit

## 描述

## 症狀

`run AutoCommit --arg op=commit` 在**撞到 `index.lock`**（別人正在跑 git）時：
`commits = 0` ／ **`blocked_repos = 0`** ／ `prestaged_repos = 0` ／ `disabled_repos = 0`，
Cmd 回 `✓ Success`。

⇒ 那份讀數跟「本來就沒東西可收」**完全同形**，而當時真的有 27 個可收的檔。
唯一的差別在 `candidate_files`，但它同時也是「有候選但依規則不該收」的正常值 ——
所以呼叫端沒有任何一格可以分辨這三種情況：

1. 有候選、全落 `__other`／`__subptr` ⇒ 不該收（正常）
2. 有候選、有群 ⇒ 收了（正常）
3. 有候選、有群、**撞鎖收不了** ⇒ 應該要喊，現在靜默

## 硬證據（evidence）

## 現場讀數（2026-08-27 21:5x ／ `D:/Unity/Bar/AgentCommands`）

| 次序 | candidate_files | commits | blocked_repos | 實際發生 |
|---|---|---|---|---|
| 第 1 次 | 82 | **0** | **0** | 什麼都沒 commit（`git log` 最新仍是我自己那筆、`git status` 仍 82 筆） |
| 第 2 次（同參數，隔數十秒） | 82 | 1 | 0 | `chore(runtime)` 8 檔 |
| 第 3 次 | 74 | 1 | 0 | `[chat]` 40 檔 |
| 第 4 次 | 34 | **0** | **0** | 什麼都沒 commit（treasury 群 27 檔還在） |
| 第 5 次（同參數） | 34 | 1 | 0 | `chore(treasury)` 28 檔 |

⇒ **同一組參數、同一份工作區，0 與 1 交替出現** ⇒ 不是分群規則的問題，是搶鎖。
旁證：同一段時間我自己的 `git_commit.py` 對同一個 repo 連續兩次拿到
`fatal: Unable to create '…/index.lock': File exists`（basecamp 在線、形狀像她在跑逐群提交）。

## 為什麼這隻值得開單（不是「重跑就好」）

**收 0 筆看起來像收工完成。** 我這次抓到它，只因為我**沒有相信 `commits=0`** ——
去讀了 `git log` 與 `git status` 才發現 82 個檔一個都沒動。
照 skill 的收尾流程走（報 SHA、報父層還指著舊 hash），第 1 次那個 `commits=0` 會被
寫成「沒有機器生成的檔要收」，而那句是假的。

📌 同族：`blocked_repos` 這個欄位本來就是為了「有東西但不收」而存在的
（detached HEAD／prestaged／disabled 都有自己的計數格）——
**撞鎖是第四種「有東西但不收」，卻沒有格子。** 欄位不是沒作用，它忠實地數了它認得的那三種。

## 建議修法（提案，不是拍板）

1. 撞 `index.lock` 的 repo 計進一個**顯式的格子**（例：`locked_repos`），而不是併進 0。
   —— 判準是「呼叫端能不能分辨」，不是「有沒有印在 Editor log 裡」。
2. `op=commit` 的回傳值加 `groups_pending`（分群後還有幾群沒落地），
   讓「收 0 筆」與「沒東西可收」在**機讀值**上分得開。
3. （可選）撞鎖時自動重試一次再放棄 —— 但**第 1 點不能被第 3 點取代**：
   重試成功也該留下「這次搶過鎖」的痕跡，否則併發問題永遠不會被量到。

⚠ 我沒有動 AutoCommit 的 code（不是我今天的射程），本單只交讀數與提案。
