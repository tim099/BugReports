# BUG-6 — persona json 被兩個序列化器輪流整檔重寫 → 語意變動在 diff 裡隱形

> `friction` / `annoying` / `resolved`　回報者：calli　認領：summit

## 描述

## 現象

`AwakenInit/personas/<P>.json` 被**兩個序列化器**輪流整檔重寫，格式互不相容：

| 寫入端 | 縮排 | 非 ASCII | 分隔 |
|---|---|---|---|
| C# `JsonData.ToJsonBeautify()`（登入 / 登出 / 後台頁） | **TAB** | `\uXXXX` escape | `"k":v` |
| Python `awakening.save_registry()`（`json.dump(indent=2)`） | **2 空白** | 中文直寫 | `"k": v` |

⇒ 每次「python 寫過之後 C# 再寫」或反之，**整份檔案的每一行都會變**。
實測 `git show --stat ca7ec1bc1` 這檔一筆狀態 commit＝**251 insertions / 244 deletions**，
而那筆真正的語意變動只有 wake_count / status 幾個欄位。

## 為什麼這值得一張單（它不會讓任何東西壞掉）

**它讓語意變動在 diff 裡隱形。**

🩸 BUG-4 的病灶（見林書籤從 13 倒退成 12）就藏在這種 diff 裡：
`git show 3b00fb4bc -- AwakenInit/personas/calli.json` 是 80+/68-，
而其中真正要看的只有一行 `last_consolidated_wake`。
**一個把書籤往回搬的變動，跟一次純排版重寫，在 review 眼裡長得一模一樣。**

而且它是雙向污染：
- 想用 `git diff` 確認「這次只改了我以為的那兩欄」→ 做不到（每次都全檔）
- 想從 history 回答「這個欄位什麼時候變成 12 的」→ 得逐版 `git show | python -c` 撈欄位
  （我今天就是這樣查的，那不該是常態手法）

## 建議修法（要拍板選一邊，本見習生不自決）

canonical 格式挑一個，兩端都照它寫：

- **A 案：跟 C# 對齊**（TAB + `ensure_ascii=True` + `"k":v`）——
  python 端改 `save_registry()` 的 `json.dump` 參數；一次性 churn 之後歸零。
- **B 案：跟 python 對齊**（2 空白 + 中文直寫）—— C# 端要改 `ToJsonBeautify` 的用法／換 writer，
  但那支是 UCL_Core 共用序列化器，影響面比 A 案大。

⚠ 本見習生**刻意沒有順手改**：這是「哪一邊是 canonical」的拍板題，
而且改錯邊的代價是所有 persona 檔一次性全churn 加上另一端從此每次反覆 ——
比現狀更糟。等 Tim / summit 指一邊。

（另有第三條路：把 registry 改成「只 patch 有變的欄位」的寫法，兩端都不整檔重寫。
C# 登入路徑其實已經是 patch-write（parse → 改 owned 欄 → 寫回），
差別只在**寫回時用了自己的排版**；所以 A/B 選一邊就夠，不必動架構。）

## 硬證據（evidence）

## ① 兩種格式的實檔證據（同一個檔，今天前後兩次寫入）

C# 寫完之後（登入 step=wake，`ToJsonBeautify`）：
```
$ git show HEAD:AwakenInit/personas/calli.json | head -4 | cat -A
{$
^I"agent":"Myth",$
^I"model":"Gemini 3.7 Flash",$
^I"layer_role":"死神見習生，嘴\u…
```
（`^I` = TAB，中文走 `\uXXXX`）

Python 寫完之後（`awakening.py consolidate` 觸發 `save_registry`）：
```
$ grep -n "last_consolidated" AgentCommands/AwakenInit/personas/calli.json
244:  "last_consolidated_wake": 23,
245:  "last_consolidated_at": "2026-08-18T01:47:19.608350Z",
```
（2 空白縮排 + `": "`；同一檔前一版是 TAB + `":"`）

## ② churn 規模（git，AgentCommands repo）

```
$ git show --stat --format= ca7ec1bc1 -- AwakenInit/personas/calli.json
 1 file changed, 251 insertions(+), 244 deletions(-)      ← 一筆狀態 commit
$ git show --stat --format= 3b00fb4bc -- AwakenInit/personas/calli.json
 1 file changed, 80 insertions(+), 68 deletions(-)        ← BUG-4 的 13→12 就藏在這裡
$ git show --stat --format= ac3910907 -- AwakenInit/personas/calli.json
 1 file changed, 5 insertions(+), 5 deletions(-)          ← 同一端連續寫，才是真實變動規模
```
⇒ 5 行 vs 250 行的差距不是內容差距，是**寫入端換手**。

## ③ 本次我自己的寫入也證實了這點

BUG-4 的 python 自癒（只改 2 欄）落檔後：
```
$ git diff --stat -- AwakenInit/personas/calli.json
 1 file changed, 245 insertions(+), 251 deletions(-)
```
**兩欄的語意變動，diff 顯示 496 行。**

## ④ 「用 diff 追欄位」實際上不可行的證明

今天要回答「`last_consolidated_wake` 什麼時候變成 12」，可用的手法是逐版撈欄位而不是讀 diff：
```
$ for c in $(git log --format=%h -12 -- AwakenInit/personas/calli.json); do
    git show $c:AwakenInit/personas/calli.json | python -c "import sys,json;d=json.load(sys.stdin);print(d.get('last_consolidated_wake'))"
  done
13 13 13 13 13 13 13 13 12 12 12 12
```
這段是本次 BUG-4 定位的唯一有效手法 —— 若排版穩定，`git log -p -S"last_consolidated_wake"` 就夠了。
