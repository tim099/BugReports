# BUG-25 — 渲染端不用訊息的 sender_name，自己重查 identities.json ⇒ 顯示舊壞資料

> `bug` / `wrong` / `resolved`　回報者：summit　認領：summit

## 描述

合一遷移後，訊息**落盤的 `sender_name` 已經正確**，但**渲染端顯示仍是舊的壞資料**。

Tim 2026-08-20 19:04 截圖：Discord 側顯示 `crest-001@basecamp`，
而同一則訊息（seq 12931）落盤內容是 `sender_id=cc`、**`sender_name=cc`**。

⇒ 渲染端沒有用訊息裡已經算好的 `sender_name`，而是**自己再查一次 `identities.json`**，
於是命中那筆壞資料：`{"id":"cc", "display_name":"crest-001"}`（一個 persona 名塞進 agent 的顯示名欄）。

⚠ 這是 BUG-22 同族的**第二層**：我修的是「訊息產生時算什麼名字」（Cmd_Tavern），
而「訊息顯示時再算一次」是另一條路徑 —— 兩條路徑各自查表，於是修一條不會修好另一條。

候選位置（未確認，明天要逐一驗）：
- `UCL_DiscordIdentityResolver.cs:53` → `LoadIdentities()`（截圖有「應用」標籤與 `→ #main`，最像）
- `UCL_ChatTavernIO.cs:990` → `LoadIdentities()`

正確修法方向（與今天的收斂一致）：
渲染端應**優先用訊息內既有的 `sender_name`**；真的要重算就走
`UCL_BankAccountProfileIO.GetDisplayName(id)` → `identities.json` → id 本身（與 Cmd_Tavern 同一順序），
而不是直接 `LoadIdentities()`。⇒ 顯示名稱的解析也該只有一份。

```json

```
`cc` 是**帳戶／agent id**，`crest-001` 是**persona 名** —— 欄位錯位。

## 對照組（證明寫入端已修好）

`Cmd_Tavern` 的解析順序已改為 accounts → identities → id，
所以**新訊息落盤的 sender_name 是對的**。錯的只有渲染那一段。
