# BUG-7 — 狀態變更會把 description/evidence 吃成「_(未填)_」（內文有 ## 小節就中）

> `bug` / `wrong` / `resolved`　回報者：calli　認領：calli

## 描述

## 現象

開單時 `description` 與 `evidence` 都填了（各數十行、走 `--arg-file`），
**但單子被 `op=claim` 動過一次之後，兩段內文都變成 `_(未填)_`。**

實例：BUG-4 / BUG-5 開單時內容完整，`op=claim` 之後兩張都只剩 32 行、內文全空；
同一天開的 BUG-6 **沒有被 claim 過**，122 行完整存活 —— 對照組就在同一個資料夾裡。

而且它**不報錯**：`op=claim` 回 Success，`op=show` 印出來的單子看起來就像
「有人開了一張沒寫內容的單」。⇒ 一張看起來偷懶的單，跟一張內容被吃掉的單長得一模一樣。

## 病灶（讀 code 確認，不是推測）

`UCL_BugReportIO.Save()` 的設計是**整檔重寫但保留內文**：狀態變更時內文欄位沒給，
就用 `ReadSection()` 把舊值撈回來（`UCL_BugReportIO.cs:129-134`）。

而 `ReadSection()` 的區塊邊界判斷是（同檔 `:262`）：

```csharp
if (aIn && aLine.StartsWith("## ", StringComparison.Ordinal)) break;
```

**它認「任何 `## `」當區塊結束。** 而 description / evidence 的內文
**幾乎一定有自己的 `##` 小節** —— 開單 skill 就是這樣教的（現象／病灶／建議修法／硬證編號）。
於是：

```
                 ← 空行
## 現象          ← 內文的第一個小節 → 誤判為區塊結束 → break，撈回空字串
```

空字串進 `Nz()` → 寫成 `_(未填)_` → 原文被整檔重寫蓋掉。**原文沒有第二份備份。**

同一個誤判也在「撈 `## 變更紀錄` 歷史」那段（`:126`）；目前變更紀錄是最後一區所以還沒咬到，
但那是**版面順序保護的**，不是判斷正確。

## 為什麼嚴重度是 wrong 而不是 annoying

`evidence` 是這套系統唯一擋「重述現象當證據」的欄位，而修單的第 ② 步就寫著
「**用單子上的 evidence 復現**」。evidence 被吃掉 ⇒ 下一個接手的人拿到一張
沒有復現依據的單，而他不會知道曾經有過。

## 建議修法

1. ✅（本次已做）區塊邊界只認**已知的頂層標題**（`## 描述` / `## 硬證據（evidence）` /
   `## 重現步驟` / `## 預期` / `## 實際` / `## 變更紀錄`），不認「任何 `## `」。
   `ReadSection` 與撈歷史那段共用同一個判定函式。
2. ⏳（未做，要拍板）**沒有 update op** —— `report` 只能新建，所以被吃掉的內文
   **用 Cmd 修不回來**（本次是手動編 md 檔補回 BUG-4 / BUG-5 的原文）。
   建議補 `op=edit --arg-file description=<檔>`，否則下次資料受損只能繼續手改。
3. ⏳ 更根本的一條：**一單一檔的內文不該靠「整檔重寫 + 解析回來」維持。**
   round-trip 解析每多一個內文慣例就多一個誤判機會（今天是 `##`，下次可能是 `---`
   ——內文若有 frontmatter 風格的分隔線，撈 frontmatter 那段會不會也誤判？沒驗過）。
