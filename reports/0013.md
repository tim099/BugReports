# BUG-13 — persona_profile tier-2 把「顯式 UCL_PP_SKIP_CMD=1」印成「Cmd 跑不通（Editor 未開？）」

> `friction` / `wrong` / `resolved`　回報者：kiara

## 描述

`_lib/persona_profile.py` 的 tier-2 訊息把「顯式跳過」講成「Cmd 跑不通」。

`_refresh_via_cmd()` 有兩條回 False 的路：
① `UCL_PP_SKIP_CMD=1`（呼叫端**顯式**要求跳過 —— 文件明寫「顯式，不猜」）
② Cmd 真的失敗（Editor 未開／timeout／exit≠0）

但 `_load()` 只有一句 stderr 涵蓋兩者：

    ⚠ [persona_profile] Cmd 跑不通（Editor 未開？）—— 改讀快照（generated_at=…），回傳值帶 _source 標記

⇒ 我在 Editor **開著**、且是我自己設 `UCL_PP_SKIP_CMD=1` 的情況下，讀到「Editor 未開？」。
資料本身沒錯（標記正確、值正確），錯的是它對原因的斷言。

危害不在這一次，在下一次：批次腳本按文件建議設了這個 env，之後有人看 log 看到
「Editor 未開？」就會去查一個根本沒問題的 Editor —— 而真正的原因（自己上游設了 env）
在訊息裡完全不可見。這跟 BUG-12 是同一族：**訊息斷言了一個 code 其實分得出來、卻沒講的原因。**
而這一個更容易被信，因為它連問號都給了，看起來像已經在推測。

**修法**：`_refresh_via_cmd()` 回傳三態（或讓 `_load()` 自己先檢查 env），
兩條路各印自己的話：
- 顯式跳過 → 「UCL_PP_SKIP_CMD=1 顯式跳過 Cmd —— 改讀快照（generated_at=…），回傳值帶 _source 標記」
- 真失敗 → 保留現行文案

⭐ 順帶一提：**這支檔正是 Phase 1（persona registry 退場案）要改的接縫**，
而 Phase 1 的驗收會大量依賴這幾行 stderr 判斷「這次讀到的是哪一層」——
一個會講錯原因的診斷輸出，在那個場景裡就是量錯的尺。
