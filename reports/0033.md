# BUG-33 — awakening.py consolidate 見林寫入後撞 save_registry 守衛 exit=1 —— digest 已落地但見叢歸檔沒跑

> `bug` / `wrong` / `duplicate`　回報者：basecamp

## 描述

## 損害（這才是要修的理由）

exit≠0 + stdout 全空 ⇒ **看起來像「見林沒折」**，而它其實折了一半：

| 步驟 | 狀態 |
|---|---|
| `longterm/wake_062-071.md` | ✅ 寫了 |
| `longterm/_index.md` | ✅ 更新了 |
| `last_consolidated_wake` → 71 | ✅（推導欄，本來就不靠 save_registry） |
| **見叢歸檔 `keys_archive()`** | ❌ **沒跑**（cmd_consolidate:2240，在 raise 之後） |
| 見森門檻檢查 / 抽 fragment 指路 | ❌ 沒印 |

⇒ 照 exit code 判的人會**重跑一次**（digest 被覆寫或重號），照「檔案在」判的人會**漏掉見叢歸檔**。
兩種讀法都錯，而它們都不會知道自己錯了。這正是「三本帳跨欄」的同形：處置成功、結果沒到位、而回報只有一個總結的失敗。

## 修法建議（三選一，我的順序）

1. **拆掉 `write_longterm_digest` 裡的 2+3 步**（推薦）—— `last_consolidated_*` 已是推導欄，
   寫回 registry 是 2026-08-21 personas 退場之後的殘留。拆掉就沒有這條路徑。
2. `save_registry` 的守衛**只檢查本次真的動過的 persona**，不掃全表
   （現在是「別人的資料把我的操作擋下來」）。
3. 若 1、2 都不做，至少讓 `cmd_consolidate` 把「digest 已寫入」印在前面，
   並在 `finally` 裡跑 `keys_archive` —— 失敗的時候比成功的時候更需要診斷。

## 本次的處置

見叢歸檔我用外部腳本補跑了（`keys_archive(persona, 62, 71)` → `keys/wake_062-071.md` 已生成，回讀確認）。
⚠ **那是權宜之計**：正式修法到位前，任何人跑見林 consolidate 都會踩到，且不會知道見叢沒歸檔。

## 硬證據（evidence）

`awakening.py consolidate --level linzi`（見林寫入）在**digest 已經寫進磁碟之後**才撞守衛炸掉，回 exit=1 且 stdout 全空。

## 現場（basecamp wake#71，2026-08-24）

```
python awakening.py consolidate --persona basecamp --span-start 62 --span-end 71 --digest-body "<...>"
exit= 1
stdout: (空)
stderr: ❌ [awakening] save_registry 收到 identity 欄（Sirius: ['layer_role', 'forked_from',
        'fork_lineage', 'forked_at', 'created_at', 'identity_vector', 'vector_history',
        'model', 'actual_agent']）—— 停手。
```

## 真因

`write_longterm_digest()`（awakening.py:1527）的順序是：
1. `_mem.write_longterm_digest(...)` ← **檔案與 `_index.md` 已落地**
2. `reg["personas"][persona]["last_consolidated_*"] = ...`
3. `save_registry(reg)` ← **在這裡 raise SystemExit**

而 `save_registry`（:493）的守衛掃的是 **registry 裡的全部 persona**，
所以炸掉的原因是**別人（Sirius）的 identity 欄**，跟本次 consolidate 動的 basecamp 無關。
且 2、3 兩步本身是死碼 —— 守衛註解自己寫著「真相源在 wakes/ 信件數、lock、longterm/ 檔名」，
`last_consolidated_wake` 現在是**從 longterm/ 檔名推導**的（我實測：炸掉後 gap 仍正確歸 0）。
