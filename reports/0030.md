# BUG-30 — AutoCommit 會把「呼叫前已 staged」的改動併進第一個群（[chat] 硬規則可被無聲違反）

> `bug` / `wrong` / `resolved`　回報者：basecamp　認領：basecamp

## 描述

`Cmd AutoCommit` 的分群只決定「它自己 stage 哪些檔」，**不會擋掉呼叫前就已經 staged 的東西** ——
於是那些檔會被併進**第一個成功的群**，掛上那個群的訊息。

🩸 現場（basecamp 2026-08-21）：我先用 `git mv` 把 21 個 persona 檔改名（進了 index），
接著跑 `run AutoCommit --arg op=commit`。結果那 21 個改名落在
`[chat] sync tavern messages & inbox (auto) [3 files]` 這筆裡 ——
訊息說 3 個檔、實際 24 個，而且是「registry 退場」被記成「聊天訊息同步」。

為什麼這一族特別貴：
- 它**不報錯**。commit 成功、檔案數那個 `[N files]` 是分群自己算的，跟實際 diff 不對帳。
- `[chat] 獨立 commit` 是 CLAUDE.md 等級的硬規則，而這條路徑會在無聲中違反它。
- 受害者是「先 stage 再跑工具」的人 —— 而那正是 `git mv` 這類操作的自然順序。

建議修法（擇一或並用）：
1. **op=commit 前先檢查 index**：`git diff --cached --name-only` 非空 ⇒ **擋下並印出那些檔**，
   要求呼叫端自己先提交或 unstage（顯式優於猜）。
2. 每群改用 `git commit -- <逐檔清單>` 這種**只提交指定路徑**的形式（pathspec 提交），
   讓 index 裡的其他東西不可能被順手帶走。
3. commit 後把實際 `--name-only` 筆數與分群預期筆數對帳，不符就 LogError。

⇒ 判準：**「我挑了哪些檔」與「這一筆實際提交了哪些檔」是兩件事**，
而工具現在只認得前者。
