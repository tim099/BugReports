# BUG-15 — BUG-14 修法把 value 放進 Required ⇒ 欄位再也無法清空，且它自己的 ContainsKey 守衛成死碼

> `bug` / `blocking` / `open`　回報者：kiara

## 描述

BUG-14 的修法（`a815b00`）把 `value` 放進 `ArgsSpec.Required`，
結果**它自己宣告要支援的用法變成不可能**：清空一個欄位。

同一支 commit 的註解寫著意圖：

> BUG-14：value 必須**顯式在場** —— GetArg 的預設值分不出「沒給」跟「給了空字串」，
> 而「沒給」多半是參數名打錯；清空欄位要顯式給 value=（空值）才算意圖。

而它也寫了正確的實作來達成這件事：

    if (!args.ContainsKey("value"))
        throw new Exception("[PersonaProfile] set 缺 value —— 參數名打錯？清空欄位請顯式給 value=（空值）");

`ContainsKey` 完全正確 —— 它分得出「沒給」與「給了空字串」。
**但它永遠跑不到**：`ArgsSpec` 的驗證在 handler 之前，而它把 present-but-empty 當成 missing。

⇒ 兩個後果：
1. `value=`（顯式空值）被擋 ⇒ **任何欄位都不能經 Cmd 清空**。Template 的 email 原值就是空字串，
   我驗收完要清回去，清不回去 —— 現在那個測試殼帶著一個測試 email 下不了台。
2. 那句 `ContainsKey` 守衛成了死碼，而它旁邊的註解仍在描述一個做不到的行為
   ⇒ 下一個人讀 code 會相信註解（**說著真話的過時文件**，這正是 BugReport 系統的立案理由）。

## 根因在框架層，不只在這支 Cmd

`UCL_CmdArgsValidator.MissingOf`：

    if (!iView.TryGetValue(aKey, out var aVal) || string.IsNullOrEmpty(aVal)) aMissing.Add(aKey);

⇒ `Required` **表達不出「必須在場、可以是空值」**。
任何「空值是合法輸入」的參數都不能用 `Required` 保護，於是每一支這樣的 Cmd 都會在
「用 Required（擋掉合法空值）」與「不用 Required（打錯參數名靜默走預設）」之間二選一 ——
BUG-14 就是後者的災，這張單是前者的災。**同一個表達力缺口的兩面。**

## 建議修法（兩層，可分開做）

- **局部（現在就能解，恢復 a815b00 的原意）**：把 `value` 從 `Required` 拿掉，
  留 handler 裡那句 `ContainsKey` 當唯一守衛 —— 它本來就是對的，只是被上游遮住。
- **框架（本質）**：讓 spec 能表達「present 但可空」（例如 `RequiredPresent`），
  且 `MissingOf` 對這類欄位改用 ContainsKey 判準。
  ⚠ 這是 §8.7 那條「兩態不得同形」換到參數層的同一個原則：
  **「沒給」與「給了空的」是兩件事，任何把它們壓成一件的驗證器都會擋掉一半的合法輸入。**

## ⚠ 附帶：錯誤訊息自我矛盾（框架層 friction，順手可改）

    缺少必要參數：[value]（你目前傳的：[actor, field, op, persona, reason, value]）

同一句話說 value 缺席、又把 value 列在「你目前傳的」裡面。
讀到這句的人第一反應一定是去檢查自己有沒有傳 —— 而他傳了。
真正該講的是「value 有給但是空的，而本 Cmd 目前把空值當缺席」。
