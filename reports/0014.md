# BUG-14 — Cmd_PersonaProfile 未宣告 ArgsSpec —— value 參數名打錯會靜默清空欄位且全鏈顯示成功

> `friction` / `wrong` / `resolved`　回報者：kiara

## 描述

`Cmd_PersonaProfile` 沒宣告 `ArgsSpec`，而它是 persona 檔的**唯一寫入通道**。

Cmd 失敗報告自己會提示這件事（逐字）：

    ℹ️ 本 Cmd **尚未宣告 ArgsSpec**，因此執行前不做參數檢查（打錯參數名會靜默取預設值）。

在多數 Cmd 上這是可接受的鬆散，但在這一支上不是，理由是它的參數語意：

- `actor` / `reason` 打錯名 ⇒ 視為缺 ⇒ **fail-loud，安全**（§8.6 的守衛救了它）
- `field` 打錯名（例：`fields=email`）⇒ 視為缺 field ⇒ 也會被擋（field 必填）
- ⚠ `value` 打錯名（例：`val=xxx`）⇒ **靜默取預設空字串 ⇒ 把目標欄清空，寫入成功、審計落行、
  快照跟上、回傳 `new_value=` 空** —— 每一層都顯示成功，而資料被抹掉了。

⇒ 現在能擋住的那幾格，是因為它們**剛好**都有必填守衛；沒有守衛的 `value` 是裸的。
這正是「看起來成功的失敗」的形狀，而且它會寫進審計檔 —— 事後查帳會看到一筆
actor/reason 都很正當、看不出異常的清空紀錄。

**修法**：在 handler 覆寫 `ArgsSpec`，把 `op` / `persona` / `field` / `value` / `actor` / `reason`
按 op 宣告 Required（`op=set` 全部必填）。
若判定 `value` 允許空字串（清值是合法操作），則**要有辦法區分「顯式傳空」與「沒傳」** ——
兩態不得同形（本案 §8.7 的同一條原則，換到參數層）。

    run PersonaProfile --arg op=set --arg persona=Template --arg field=email \
        --arg value="SHOULD-NOT-LAND@test.invalid" --arg reason="…"   ← 故意不給 actor

    真正的 exit = 2
    [PersonaProfile] set 失敗：actor 與 reason 必填（§8.6）—— …匿名寫入不收
    → 值未落地、審計未增行（實測：行數 3→4 只增在成功那筆）

⇒ 證明守衛存在且有效；也證明**擋下來的機制是「欄位必填」而不是「參數名檢查」** ——
所以沒有必填守衛的 `value` 不在保護範圍內。
