# BUG-34 — Task 寫檔流程沒有 lock —— 回傳檔／單檔／index 計數器三處在 per-persona 並行 lane 下會靜默互蓋

> `bug` / `wrong` / `resolved`　回報者：basecamp

## 描述

`AgentCommands/Tasks/_last_task_report.md` 是**全域共用單檔**，任何人跑 `Cmd_Task` 都會覆寫它。
於是 `run_cmd` 印出路徑之後，**那個路徑底下的內容不保證還是我那次的** ——
而檔案 header 上的 `persona=` 是**寫檔那個人**的名字，不是讀檔那個人的。

## 為什麼這格值得修（不是潔癖）

`op=kanban` 的內容是全域的，所以撞到的那次數字剛好沒錯 —— **而那正是問題**：
它讓「共用單檔」這件事在最無害的 op 上不會被發現。
換成 `op=show` / `op=list --arg assignee=<me>` 這種**帶 persona 語意**的 op，
兩個人幾秒內先後跑，後到的人就會讀到別人的視圖，而 header 上的名字**看起來是對的**。

📌 同族：**「我送出了」不等於「對方收到了」** 的檔案版。

⚠ 我這次是靠「header 上的名字跟我不一樣」才發現的。
**如果那次剛好是另一個 basecamp session 跑的，我永遠不會發現。**

## ⚠ 而回傳檔只是症狀 —— Tim 2026-08-25 指出真正的範圍是**寫檔流程要 lock**

回傳檔被覆寫是**唯一會被看見**的那一格（因為 header 帶名字）。同一個併發窗口底下還有兩格
**不會被看見**的：

1. **`tasks/<index>.md` 的 read-modify-write**：`Cmd_Task` 每個 op 都是「載入 → 改 → 存回」。
   兩個 persona 同時對**同一張單**留言／改狀態，後寫的會**整檔覆蓋**前一筆 ——
   而時間線是 append-only 的**內容**，不是 append-only 的**寫法**，所以丟失不報錯。
   🩸 這不是理論：昨天 0015/0016/0017 同時有我的 QA 意見與 gura 的對帳留言落在同一批檔上。
2. **index 計數器**：`IncrementAndGetIndex()` 若不是原子的，兩張單同秒 create 會拿到同一個號碼
   （對照：`Cmd_BugReport` 用同一個模式）。

⇒ **修法的射程應該是「Task 的寫檔流程」整體，不是那份報告檔。**
📌 只修被看見的那一格，會漏掉沒人發現的那一格；而沒人發現的那一格，永遠不會有人來說。

## 建議修法

- **(d) 【Tim 指示，優先】寫檔流程加 lock** —— 進入寫入區前取檔案鎖（本專案 `_session/` 已有
  per-persona lock 的既有原語可抄），涵蓋 `tasks/<index>.md`、index 計數器、報告檔三者。
- (a) 報告檔改 per-persona：`Tasks/_last_task_report_<persona>.md`（症狀解，可與 (d) 併行）
- (b) `run_cmd` 印出的路徑改指向 `_cmd_results/<job_id>` 那份專屬落檔
- (c) `run_cmd` 回讀 header 比對自己的 persona，不符就喊 ——
      最便宜，但只是把靜默失敗變成吵鬧失敗，**沒有解決共用**

⚠ 驗收時要注意：(a)(b)(c) 都只治回傳檔那一格。**單檔覆蓋那格沒有 header 可以對，
所以它的驗收必須是「兩個 process 同時寫同一張單，事後兩筆留言都還在」，不能靠肉眼。**

## 硬證據（evidence）

## 硬證 ①：同一份檔案在 13 秒內換了兩次主人

| 時刻（local） | 誰跑的 | 那一刻檔案 header 第一行 |
|---|---|---|
| 08:19:47 | **我**（`--persona basecamp`，`op=kanban`，job `20260825-081947-dd0830-task`） | —（還沒讀） |
| 08:19:53 | summit | `# Task op=kanban persona=summit  ts=2026-08-25 08:19:53+08:00` |
| 08:20:00 | gura | `# Task op=kanban persona=gura  ts=2026-08-25 08:20:00+08:00` |

⇒ 我跑的是 `081947` 那筆，而我讀到的那份 header 寫著 **summit**；
隨後系統提示該檔再次變更，header 變成 **gura**。

三筆 job 的專屬落檔都在（證明分格落檔存在，只有人可讀那份是單一格）：
```
AgentCommands/_cmd_results/20260825-081947-dd0830-task.json   ← 我的
AgentCommands/_cmd_results/20260825-081952-694d40-task.json   ← summit
```

## 硬證 ②：並行是**真的**，不是我推測的 —— 而且這一族在本專案已經咬過一次

`UCL_AgentCommandRunner.cs` L68-75 自己寫著（2026-08-16 血證，Tim 拍板「讓 Cmd 能平行跑」）：

> 原本這裡是一顆 `static readonly List<string> s_CurrentCmdOutputs`，每筆 cmd 起跑前 Clear。
> 那個設計**只在串行下正確** —— **queue 依 persona 分 lane 後 watcher 會並行派遣**，
> 兩條 lane 會互相 Clear／互相寫入，而結果是「拿到別人的回傳檔路徑」，**完全無聲**。

⇒ 當時的修法是改成 **per-cmd context，由 `args["_cmd_id"]` 顯式索引**。
📌 `_last_task_report.md` 是**同一隻病的殘留**：它還是那顆全域 slot，只是換成了磁碟上的檔。
**修法的樣板已經在同一個檔案裡了。**

## 硬證 ③：index 計數器是 read-then-write，不是原子的

`UCL_TaskIO.IncrementAndGetIndex()` L75-91：
```
int aCounter = ReadCurrentIndex();      // 讀
...
int aNext = aCounter + 1;
File.WriteAllText(IndexPath, aNext…);   // 寫  ← 中間沒有鎖
return aNext;
```
兩條 lane 同時進來會拿到同一個 `aNext` ⇒ 兩張單寫同一個 `tasks/<index>.md`，後寫的整檔蓋掉前一張。
⚠ 檔內既有的自癒（`aDiskMax > aCounter` 就拉齊計數檔）**只救得了之後的單，救不了已經被蓋掉的那張** ——
而且它拉齊的動作會讓事後回頭看時**看不出曾經撞過號**。

## 硬證 ④：單檔是 read-modify-write，時間線的 append-only 只在內容不在寫法

`Cmd_Task` 每個 op 都是「`UCL_TaskIO.Load*` → 改物件 → `UCL_TaskIO.Save(e, …)`」整檔覆寫。
兩個 persona 同時對**同一張單**留言／改狀態 ⇒ 後寫的整檔覆蓋，前一筆留言消失，**不報錯**。
🩸 這不是理論：2026-08-24 `tasks/0001 0005 0015 0016 0017 0019` 同時含我的 QA 意見與 gura 的
對帳留言與 summit 的 wrapup，全落在同一批檔上（見 summit 的 commit `2ce8c11` 訊息自述）。

## 重現指令

```bash
python <UCL_Core>/Tools~/AgentCommands/run_cmd.py --persona A run Task --arg op=list --arg assignee=A
python <UCL_Core>/Tools~/AgentCommands/run_cmd.py --persona B run Task --arg op=list --arg assignee=B
head -1 AgentCommands/Tasks/_last_task_report.md    # ← 只會剩下後到那個人的
```
