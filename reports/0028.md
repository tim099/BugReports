# BUG-28 — Cmd_Plurk op=post 的回傳檔沿用 preview 文案，開頭寫「本 op 不送」而實際已送出

> `bug` / `wrong` / `resolved`　回報者：Sirius

## 描述

`op=post` 的回傳檔在**同一份檔案裡先說「不送」再說「已送出」**，而讀者是從上往下讀的。

## 硬證據（evidence）

plurk_post.md 第 14 行「## 將送的 payload（本 op 不送）」與第 29 行「⛔ 本 op 不上傳。」，同檔第 31 行「圖片已上傳: https://images.plurk.com/4fjKHACogV3bXuenbEW28M.png」、第 33-35 行「## post（已送出）／http: 200／plurk_id: 358452101571566」。同一次執行、同一份回傳檔，前後互相否定。

## 實際

```
## 將送的 payload（**本 op 不送**）      ← 第 14 行
...
　⛔ 本 op **不上傳**。                   ← 第 29 行
- 圖片已上傳: https://images.plurk.com/…  ← 第 31 行（正好相反）
## post（已送出）                        ← 第 33 行
- http: 200  plurk_id: 358452101571566
```

`op=post` 顯然重用了 `op=preview` 的渲染段落，而那段的文案是為 preview 寫的
（「本 op 不送」「本 op 不上傳」）。在 post 的回傳檔裡，那兩句是**假的**。

## 為什麼值得修（不是排版潔癖）
我照流程 lint → post，Cmd 回 Success，然後打開回傳檔第一眼看到「本 op 不送」——
**我當場以為沒發出去。** 如果我照那句話的意思重跑一次 post，就會發出**第二則重複的噗**
（而已發出的噗不能靠 amend 收回）。
⇒ 這個文案的失敗模式是「誘導使用者重試一個不可逆的動作」。

## 建議修法（擇一，皆屬「讓誤讀不可能」層）
1. post 路徑渲染那段時把標題換成「## 送出的 payload」，並拿掉「本 op 不送／不上傳」兩句。
2. 或把「已送出」結果**移到檔案最上面**（結論先行，過程在後）。
3. 最低成本：那兩句改成「（preview 時不送；本 op 會送）」——
   但這仍要求讀者讀完整句才不誤解，效果比 1、2 差。
