# BUG-8 — 父層 bump 引用子 commit 摘要 → 重複關單並把 commit_sha 覆寫成 pointer bump

> `bug` / `wrong` / `open`　回報者：calli

## 描述

## 現象

在**父層 bump** 的 commit 訊息裡「引用」子 commit 的摘要時，只要那段引用含
`Fixes BUG-<n>` 字樣，`git_commit.py` 就會**再關一次單**，並把 `commit_sha`
覆寫成那筆 bump 的 SHA。

實例（2026-08-18 calli wake#24 收工）：主專案 bump `0cdc0c6` 只是三個 pointer 位移
（`3 files changed, 3 insertions(+), 3 deletions(-)`），但因為訊息裡列了子 commit 摘要
（含 `Fixes BUG-4` / `Fixes BUG-5` / `Fixes BUG-7`），三張單的 `commit_sha` 全被改成 `0cdc0c6`。

⇒ 於是單子指著一筆**沒有修過任何東西的 pointer bump**。
日後要復盤「這 bug 是怎麼修的」，`git show 0cdc0c6` 只會看到三行 hash 位移。

## 為什麼算 wrong 而不是 annoying

`commit_sha` 是這套系統對「修法在哪」的唯一索引。它指錯地方時：
- 單子看起來**完全正常**（有 SHA、狀態 resolved、變更紀錄有兩行）
- 而那個 SHA 拿去 `git show` 得到的是不相關的內容 —— **不會報錯，只會誤導**
- 已關的單沒人會回頭看，所以這個錯會一直躺在那裡

（本次變更紀錄兩行都留著，所以真相還撈得回來 —— 但那是運氣，不是設計：
第一次關單那行剛好帶了正確 SHA。）

## 建議修法（三條，任一條就能擋掉）

1. **已 resolved 的單不要覆寫 `commit_sha`** —— 重複命中只追加變更紀錄行，
   或印一行「BUG-n 已由 <舊 SHA> 關過，本次不覆寫」。
   （最小改動，且語意最正確：修法就是修法，後來的 bump 不是。）
2. **只解析訊息「自己的」那一段**：`Fixes` 關鍵字若出現在引用區塊
   （行首 `-` / `>` / 縮排 4 空白 / 反引號區塊內）就不算。
   ⚠ 這條要小心 —— 版面判斷會有邊界，不如 ①。
3. **pointer-only 的 commit 不觸發關單**：staged diff 全是 gitlink（mode 160000）時跳過閉環，
   並印一行說明。那類 commit 在定義上不含修法。

## 補充：本次已做的資料修復

手動把三張單的 `commit_sha` 改回真正修好它的那筆
（BUG-4 → `db8dd2ed`、BUG-5 → `b91c24add`、BUG-7 → `aa84386f`）。
變更紀錄那兩行**沒有刪** —— 帳不美化，只修那個會誤導的欄位。
⚠ 又一次撞到 BUG-7 同款的事：**這套系統沒有 update op**，資料修復只能繞過 Cmd 手改 md。

## 硬證據（evidence）

## ① 那筆 bump 的內容（它沒有修任何東西）

```
$ git show --stat --format= 0cdc0c6
 AgentCommands           | 2 +-
 Assets/Plugins/UCL_Core | 2 +-
 Docs/Glossary           | 2 +-
 3 files changed, 3 insertions(+), 3 deletions(-)
```
三行都是 gitlink（submodule pointer）位移。

## ② 工具的 console 輸出（關單真的跑了）

```
$ git_commit.py --repo . --message-file <bump 訊息>
🐛 BUG-7 已自動關單（0cdc0c6）
🐛 BUG-5 已自動關單（0cdc0c6）
```
⚠ **更正（開單後 20 分鐘自己推翻）**：原本這裡寫「BUG-4 沒有印出來但檔案被改了 ⇒
印出來的與實際改到的不一致」。**那是錯的** —— 三張單都有印，是我自己用 `tail -2`
截掉了前面的輸出，然後把截斷當成工具的不一致。
⇒ 錯的證據比沒有證據更糟（憲法④ 真數）。留著這段是因為它本身是一筆帳：
**用截斷過的輸出當證據，會製造一個不存在的 bug。**

## ⑥ 真正的判準（讀 code，不是推測）

```
$ grep -n "Fixes" git_commit.py
185:    for m in re.finditer(r"\bFixes\s+BUG-(\d+)\b", message, re.IGNORECASE):
```

`re.IGNORECASE` + 全文掃 ⇒ **訊息裡任何位置**出現 `Fixes BUG-<n>` 都算，
包含「引用子 commit 摘要」、包含「描述這個 bug 本身」。

🩸 實測第二次自摔：我在 BUG-8 的資料修復 commit 訊息裡寫了一句
「（含 Fixes BUG-4/5/7 字樣）」來**說明這個 bug**，於是 BUG-4 又被關了一次、
`commit_sha` 又被覆寫成那筆 commit 的 SHA。

⇒ **描述觸發器的那句話本身就是觸發器。** 這一格讓建議 ① 從「比較正確」變成「必要」：
只要「已 resolved 不覆寫 `commit_sha`」，上面兩次自摔都不會留下錯資料。

## ③ 單子被改成什麼（修復前）

```
$ grep -n "^commit_sha" reports/0004.md reports/0005.md reports/0007.md
reports/0004.md:11:commit_sha: 0cdc0c6
reports/0005.md:11:commit_sha: 0cdc0c6
reports/0007.md:11:commit_sha: 0cdc0c6
```

而變更紀錄留下了兩行（第一行才是真的）：
```
- 2026-08-18T14:14:34.507Z　resolved　b91c24add —— 由 git_commit.py 自動關單（訊息含 Fixes BUG-5）
- 2026-08-18T16:08:33.365Z　resolved　0cdc0c6  —— 由 git_commit.py 自動關單（訊息含 Fixes BUG-5）
```

## ④ 真正修好它們的那三筆（對照）

```
db8dd2ed [fix] 見林書籤加磁碟對帳（兩端）＋ 關係區塊 fail-soft 不准說謊     ← BUG-4
b91c24add [fix] _lib/ucl_paths.py 鏡像 → 轉發 shim（實作只留 UCL_Core 一份）  ← BUG-5
aa84386f [fix] 問題回報單的區塊邊界只認已知標題                            ← BUG-7
```

## ⑤ 復現指令（給修的人）

```
# 1. 隨便開一張測試單並用一筆真的修法關掉（記下 SHA_A）
# 2. 做一筆 pointer-only 的 bump，訊息裡引用步驟 1 的摘要（含 Fixes BUG-n）
# 3. grep "^commit_sha" reports/<n>.md
```
驗收標準：`commit_sha` 應仍是 `SHA_A`，而非 bump 的 SHA；
或工具印出「已由 SHA_A 關過，本次不覆寫」。
