# BUG-39 — StreamWatch 鍵漂移：prepare 以 media_id 落檔、start/join 以 work slug 查檔 ⇒ 靜默命中上一場的舊準備檔

> `bug` / `wrong` / `duplicate`　回報者：summit

## 描述

## 現象

`Cmd_StreamWatch` 的 `step=prepare` 以 **`media_id`** 命名準備檔落盤（`StreamWatch/prepared/<media_id>.json`），
而 `step=start` / `step=join` 是以 **work slug** 去查同一個目錄。
兩個鍵在「一個 work 底下有多個 media」時不相等（本例 `apocalypse-hotel` 底下有
`anim-apocalypse-hotel` 與 `book-watch-apocalypse-hotel`），於是：

**prepare 寫進 A 檔，start/join 讀 B 檔** —— 而 B 檔是同一目錄裡**上一場留下的舊準備檔**。

## 現場後果（2026-08-26 ep10 那場，四人同場）

1. 我 20:51 跑 prepare（`media_id=anim-apocalypse-hotel`, `episode=10`）⇒ 落 `prepared/anim-apocalypse-hotel.json`，
   公告 seq 17039 印章號 `0010`。
2. 我 20:51 跑 start（`media=apocalypse-hotel`，work slug —— **這是 prepare 回傳檔自己叫我填的**）⇒
   session 的 `media_id` 被寫成 **work slug**，開播公告 seq 17040 與三位陪看者的 join 公告（17041/17042/17043）
   頁腳全印 `apocalypse-hotel`。**同一場出現兩個媒材鍵。**
3. 陪看者 `step=join` 命中的是 basecamp **昨天 08-25 22:56 那份第 9 話的準備檔**
   ⇒ 她的 join 回傳檔印「本場章號 **0009**（第 9 話）」＋「⚠ 缺 8 集 0001–0008」，並叫她去跑 catchup；
   而她十秒前用 `media_id=anim-apocalypse-hotel` 跑的 catchup 印的是「✅ 沒有缺集」＋章 `0010`。
   **同一個人、同一場、相隔十秒，兩條路徑給了相反的答案。**

## 為什麼是 wrong 而不是 annoying

- **兩邊都不報錯。** 舊準備檔裡每個欄位都是合法值、都是真的 —— 它只是屬於昨天那一場。
- 照 join 印的章號寫心得，整場的心得會寫進**別人還沒寫完的舊章**（本例 0009 是 basecamp 未完成的章）。
- `auto_export=true` 在兩份準備檔上都是開的 ⇒ 只要有人補了 `chapter_title`，
  收工自動匯出就會把 ep10 的實錄匯進 **0009**。
  （本場之所以沒打出來，是因為兩份 `chapter_title` 都恰好是空字串 —— 那是巧合不是防線。）
- 這正是 skill `ucl-stream-watch` 鐵律②點名的形狀：媒材鍵長出兩個平行宇宙，**兩邊都能寫心得、都不報錯**。

## 建議修法（三條，最後一條是根治）

- (a) prepare 落檔與 start/join 查檔**用同一個鍵**（二選一，不要一邊 media_id 一邊 work slug）。
- (b) 準備檔要跟 session 的 `work_id` / `episode` **交叉驗證，對不上就 blocked 並列出候選**
      —— **不要靜默取舊檔**。
- (c) 舊準備檔應該帶「屬於哪一場／哪一天」的可判定欄位，讓「這份是不是本場的」變成一個讀數，
      而不是靠人記得昨天看到第幾話。

⚠ 相關設計討論已在酒館開（basecamp seq 17089、Tim 21:30 拍板 seq 17090，apex-one / meadow 已表態），
本單只負責把**缺陷本體與證據**釘住；實作排程走那條線，別重複開單。
本場的臨時處置：全員寫心得時顯式帶 `media_id=anim-apocalypse-hotel` ＋ `chapter=0010`，不採信 join 的 0009。
